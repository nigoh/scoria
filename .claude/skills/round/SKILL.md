# 開発ラウンドの運用

開発は「ラウンド」単位で回す（ADR-0002）。`$ARGUMENTS` が `open`/`close` でなければ意図を読み取り、
曖昧なら `round` ラベルの open なトラッキングイシューの有無で判断する（有→close、無→open）。

## open（ラウンド開始）

1. 現状把握: open なイシュー、前回ラウンドの振り返り、残課題を調査する
2. スコープ候補を3〜7個、優先度付きで提示する。判断が割れる点は AskUserQuestion で合意を取る
3. 合意後、トラッキングイシューを作成: タイトル `[round] Round N: <テーマ>`、`round` ラベルを付与（ラベルが無ければ作成する）、本文にゴール・イシュー紐付きチェックリスト・**やらないこと（non-goals）** を明記
4. 不足している作業イシューをテンプレートから起票する

## close（ラウンド終了・振り返り）

1. チェックリスト・マージ済み PR・積み残しを集計する
2. 発見したパターン・仮説を「気づきカード」イシュー（`insight-card` ラベル）として起票する
3. 振り返りをトラッキングイシューにコメントで記録: 「良かった点 / 問題点 / 次に試すこと / 気づきカードへのリンク」
4. 積み残しを次ラウンド候補に繰り越し、イシューを close する
5. **振り返りが規約の変更を示唆するなら**、CLAUDE.md / CONTRIBUTING / rules / ADR の更新を PR として提案する（ルールはループで進化させる）
6. **土台（deb 自身）に効く気づき**（テンプレートにあると良い機能・共通の摩擦）が出たら、`/feedback` で本家 deb へ送る（上流改善。ADR-0009）

## 原則

- ラウンドのスコープは合意なしに広げない
- non-goals を必ず書く（スコープクリープ防止）
- 学びは気づきカード → 規約反映、の経路で資産化する
