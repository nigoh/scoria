# 修正提案 → 選択 → 忠実実装

いきなり実装しない。まず現ソースに基づく修正案を出し、選択後に実装する。
単純・自明な修正（typo、明白な1行バグ）はこのフローを使わず直接実装してよい。

## 1. 現状把握

- 対象のソースを読み、問題の根本原因と影響範囲を `file:line` 単位で特定する
- 保護ファイル（ロックファイル・Accepted ADR・シークレット、スタック導入後は生成物も）に触れる案になっていないか確認する

## 2. 提案アーティファクト（固定様式）

`artifact-design` スキルを読み込んだ上で、次の**固定ブロック順**の HTML アーティファクトを作成・公開する:

1. **問題**: なぜ直すか、発生条件、根拠となる `file:line`
2. **現状**: 全案の共通起点となる現ソース抜粋（diff の文脈として提示）
3. **案カード A/B/C**（2〜4案、全カード同一構造）: 概要 / 変更点 / Before→After diff / 長所・短所 / 影響（層・テスト・移行）/ 工数 S・M・L。ちょうど1案に「推奨」バッジを付ける
4. **比較表**: 案 × 固定軸（工数 / リスク / 影響範囲 / テスト / diff サイズ）。この表だけで選べること
5. **選び方**: 記号1つで選択可能に。案の混合も可と明記

- diff は実在のコードに基づく、コンパイル可能な現実的なものにする（架空 API 禁止）
- 公開したら**必ず停止**してユーザーの選択を待つ（`auto-implement` 指定時を除く）

## 3. 忠実実装

- 選ばれた案を**そのまま**実装する。実装中に得た改善案は提案として報告し、勝手に混ぜない
- 再発防止テストを併設する（バグ修正の場合は red→green）
- `bash scripts/check.sh` で緑を確認して完了報告する
