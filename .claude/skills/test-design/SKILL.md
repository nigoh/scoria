# テスト網羅性の設計

行き当たりばったりでなく、観点 → アーキテクチャ → 技法の順に設計する（IPA 6章、`docs/process/verification.md`）。
成果物は `docs/process/templates/test-design.md` を雛形に起こす。

## 1. テスト要求分析（観点の抽出）

対象の要件（REQ/NFR）を起点に「何を確かめるか」の観点を洗い出す:
機能／境界・データ／状態遷移／組み合わせ／異常系・例外／非機能（性能・セキュリティ等）。

## 2. テストアーキテクチャ設計（レベル割付）

各観点を適切なテストレベルへ割り付ける（V字モデル、`lifecycle.md`）:
- 単体（TEST-unit）: 純粋ロジック・境界・分岐
- 結合（TEST-integration）: モジュール間の IF・データ受け渡し
- システム（TEST-system）: エンドツーエンドの機能・非機能
- 受入（TEST-acceptance）: 要件の受入基準の妥当性確認

## 3. 技法の適用

- **同値分割・境界値分析**: 入力空間を代表値＋境界で被覆
- **直交表・ペアワイズ**: 組み合わせ爆発を2因子間網羅で圧縮（全網羅せず欠陥検出力を保つ）。因子と水準を表にする
- **状態遷移テスト**: 状態と遷移（正常・異常）を被覆
- **シナリオテスト**: 現実の利用フローで結合的に検証（ピンポイント）

## 4. トレーサビリティの付与

各テストケースに `TEST-<レベル>-<3桁>` を採番し、検証対象を `Verifies: REQ-... / NFR-... / DES-...` で明記する
（`docs/process/traceability.md`）。これにより `check-traceability.sh` が要件被覆を検証できる。

## 5. 実装

テストコードは `test-engineer` エージェントに委譲するか自分で実装する。バグ由来なら red→green。
仕上げに `bash scripts/check.sh` で緑と要件被覆（100%）を確認する。
