# ドキュメント構成の規約（ピラミッド原則。機械検査は scripts/check-docs-structure.sh）

読み手は「結論を先に受け取り、図で掴んでから、文で確かめる」。バーバラ・ミントのピラミッド原則を
このリポジトリの文書（`docs/` のサイト HTML・README・`docs/` の Markdown）の**強い規約**として適用する。
HTML については機械検査（`scripts/check-docs-structure.sh`）が構造マーカーで落とす。
Markdown（README / docs/）と、意味に踏み込む項目（MECE・図と本文の一致など）は人のレビュー（doc-auditor）で見る。

## ピラミッド原則（すべての節に適用）

- **結論 → 根拠 → 詳細** の順に書く。節の見出しは読者の問い（Question）、その直後に答え（Answer）を置き、
  下に支える根拠、さらに下に詳細（手順・コード・表）を並べる。上の階層は下の階層の要約になっていること。
- **結論は1文**（句点は1つまで）。1文にまとまらないなら、それは頂点になっていない＝節を割る。
- 同じ階層に並ぶ項目は **MECE**（互いに排他・合わせて漏れがない）を目指す。並べる順は
  時系列・構造・重要度のいずれか1つの原理で統一する（原理を混ぜない）。
- **見出し階層を飛ばさない**（h2 の次に h4 を置かない）。深い階層に落ちるときは中間の見出しを置く。

## 図が先、文が後

- 節の中では、**結論の直後に図**（`<figure>`）を置き、文章はその補足として続ける。図が呼び水になり、
  視覚的に理解してから文章で確かめる順にする。
- 判定の単位は**見出しブロック**（ある見出しから次の見出しまで）。ブロックに図があるなら、
  最初の `<figure>` は最初の本文段落（`.answer` 以外の `<p>`）より前に置く。
- 図には `<figcaption>` を付け、図だけ見ても何の話かわかるようにする（人のレビュー）。
- **アニメーションは reduced-motion を尊重する**。`@keyframes` を使うファイルには
  `prefers-reduced-motion` の指定を必ず置き、動きを止められるようにする。

## 用語の初出

用語集の語は**初出で注釈**を付ける。注釈は次のどちらかで書く（属性値は二重引用符）。

- `<abbr title="1行の定義">用語</abbr>` … 基本形
- `class="term"` を持つ要素（`<span class="term" title="1行の定義">用語</span>` など）

用語集の正本（この語彙で機械検査する）:
`deb` / `steering` / `機構` / `品質ゲート` / `フック` / `Stop フック` / `ADR` / `MAPE-K` / `fail-closed` /
`トレーサビリティ` / `テーラリング` / `ラウンド` / `ドラフト PR` / `サーキットブレーカー` / `safe-state` / `shdoc`

表記は用語集どおりに揃える（`ドラフト PR` を `ドラフトPR` と書くと同じ語と見なされない）。
**この一覧が正本**であり、`scripts/check-docs-structure.sh` の語彙と一致することを機械検査する
（片方だけ増やすと「規約には書いたが検査されない語」が生まれるため）。語を増減するときは両方を同じ順・
同じ表記で直す。

**初出と数えない場所**（誤検知で執筆が窮屈にならないための除外規則）:

- `<head>` の中（`<title>` / `<meta>`）、`<script>` / `<style>` の中身
- `<code>` / `<pre>` / `<kbd>` / `<samp>` の中（識別子・コマンドとしての出現）
- `<nav>` と `<footer>` の中（ナビゲーション・共通フッタ）
- `<svg>` の中（図中のラベル。注釈タグを置けないため）
- 見出し（h1〜h6）の中（注釈を入れると見出しが読みにくくなるため）
- 用語集自身（`class="glossary"` を持つ要素の中の定義）
- タグの属性値・HTML コメント
- 語の一部としての出現（`deb` は `debug` の中では初出と数えない）

より広い語を注釈すれば、その中に含まれる語も満たしたことになる（`Stop フック` を注釈すれば `フック` も満たす）。

## HTML の構造マーカー（機械検査の契約）

| 目的 | マーカー | 備考 |
|---|---|---|
| 節の結論 | `<p class="answer">` | 節の見出しの**直後**に置く。他クラスとの併記可（`class="answer lead"`） |
| 図 | `<figure>` / `<figcaption>` | 結論の直後、本文段落より前 |
| 用語の注釈 | `<abbr title="…">` / `class="term"` | 初出のみ必須 |
| 用語集 | `class="glossary"` | この中の出現は初出と数えない |
| 検査範囲 | `<main>` | `<main>` があればその中だけを検査する（無ければ文書全体） |

- 検査対象は `docs/` 配下のサイト HTML（現状 `docs/reference.html`。生成物なのでマーカーは
  `scripts/build-docs.sh` のテンプレート側に入れる）。リポジトリ直下の `index.html` は Vite の
  エントリーポイント＝アプリの実体であり文書ではないので、検査対象に含めない。
- 見出しを持たない構造用の `<section>`（レイアウト目的のラッパー）は検査対象外。
  逆に**見出しを持つ `<section>` は必ず結論段落から始める**（入れ子の `<section>` もそれぞれ検査される）。
- `</p>` を省略しない（結論段落の範囲が決まらなくなる）。
- 判定に必要な `gawk` が無い環境では、検査は「判定不能」を合格に倒さず明示メッセージで落ちる（fail-closed）。

## 検査しないもの（人のレビューで見る）

- MECE か・根拠の並べ方の原理が統一されているか・上の階層が下の要約になっているか（意味の判断）
- 図の内容と本文が一致しているか、`<figcaption>` が図を説明しているか
- README / docs/ の Markdown（構造マーカーが無いため機械検査しない。書き方の原則は同じ）
