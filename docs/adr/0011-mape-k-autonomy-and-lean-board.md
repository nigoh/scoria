# 0011: MAPE-K の自律運用（夜間スケジュール・自動 Execute）と計画イシューのスリム化

- Status: Proposed
- Date: 2026-07-19
- Deciders: nigoh, Claude

## Context（背景）

ADR-0010 で MAPE-K 夜間セルフ改善を導入し、数周まわして機能を確認した。運用に載せる段で3つの論点が出た。

1. **計画イシューの肥大化**: 1本のイシューを使い回す設計は「チェックを入れるだけ」の承認 UX を保てる一方、
   完了項目や履歴が積もるとイシューが肥大化して見通しが悪くなる。
2. **周回頻度**: これまで `/mape-night` は手動起動だった。M/A/P は読み取り専用で安全・安価なため、
   自動スケジュールに載せたい。何周まわすかの方針が未定だった。
3. **自動改善の範囲**: 「壊しうる」Execute をどこまで自動化するか。無人で走らせるときの安全境界が未定だった。

制約: ADR-0010 の絶対原則（1周1件・トピックブランチ + PR・main を直接触らない・**PR まで、マージはしない**・
サーキットブレーカー）は維持する。ADR-0010 は main マージ済みで編集不可のため、本 ADR で拡張する（supersede しない）。

## Decision（決定）

### D1. 計画イシューは「1本の板＋完了を畳む」でスリムに保つ

- 計画イシューは引き続き**1本**（ラベル `mape` ＋タイトル `🌙 MAPE-K`）を使い回す（承認 UX を維持）。
- **完了項目は本文の `<details>「✅ 完了ログ」` に畳む**。`mape/plan.sh` が実行台帳（`ledger.jsonl`）の
  `green` から完了ログを**決定論的に生成**する。イシューは常に「今のアクティブな提案＋畳んだ完了ログ」だけを表示。
- 履歴の正本は `knowledge/PROGRESS.md`。イシューは“今の板”に徹し、サイズをほぼ一定に保つ。
- 未チェックのまま一定周回を過ぎた提案は `knowledge/BACKLOG.md` の「アーカイブ」へ退避（計画を腐らせない）。
- 将来プロジェクトが大きくなり1本で収まらなくなったら「1項目=1イシュー」へ移行する（再検討トリガー）。

### D2. M→A→P は毎晩1回、自動で回す

- `cron` Routine で `/mape-night` を**毎晩1回**起動する（読み取り専用ゆえ安全・安価）。
- 「N 周だけ」ではなく「毎晩1周を継続」する。HEALTH 推移が積み上がり、周回ごとに判断が良くなる前提を活かす。

### D3. Execute は夜間に自動化する。ただしゲートは維持（チェック済みのみ・PR まで）

- `cron` Routine で `/mape-execute` を毎晩（M→A→P の後）起動する。ただし自動実行時の安全境界を厳格化する:
  - **チェック済み・未着手を1周1件だけ**（auto は既定チェック済み、approve は人手チェック必須）。
  - **consult 項目は無人実行では実装しない**（対話で質問できないため）。スキップして計画イシューに理由を残す。
  - **緑のときだけドラフト PR**。**マージは常に人間**（PR まで、が絶対原則）。
  - サーキットブレーカー tripped なら Execute せず通知（連鎖失敗の暴走を止める）。
- 自律レベルは `knowledge/POLICY.md` の「自律レベル」で管理し、いつでも手動運用に戻せる。
- `issues.edited` Webhook による即時 Execute は次段の拡張として残す（本 ADR では採用しない）。

## Options Considered（検討した選択肢）

### D1 の選択肢

#### 案1: 1本の板＋完了を畳む（採用）
- 長所: URL 1本・チェック UX 維持。完了は畳むのでサイズ一定。履歴は PROGRESS.md が正本。実装が小さい。
- 短所: 提案が同時に大量に出ると板が長くなる（当面はスコア上位のみ掲示で緩和）。

#### 案2: 1項目=1イシュー
- 長所: 肥大化が原理的に起きない。PR マージで自動 close。
- 短所: 承認が「チェック」でなくラベル/assign 運用になり、UX の要（見てチェックするだけ）が崩れる。イシュー数が増える。

#### 案3: 1周回=1イシュー（毎回新規・前回 close）
- 長所: サイクル単位で clean。
- 短所: 人手のチェックが周回をまたいで引き継がれず、板の連続性を失う。

### D2/D3 の選択肢

#### 案1: M/A/P を自動・Execute はチェック済みのみ自動・マージは人間（採用）
- 長所: 安全境界が明確（読み取りは全自動、破壊的操作はゲート付き自動、マージだけ人間）。ADR-0010 の原則を保つ。
- 短所: 完全放置にはならない（マージとレビューに人が要る）。それは意図した安全性。

#### 案2: 完全自律（auto tier は緑 CI で自動マージ）
- 長所: 人手が最小。
- 短所: 「PR まで、マージしない」原則を破る。誤検知やレビュー漏れが main に入り得る。現段階では過剰。

#### 案3: 自動化しない（手動のまま）
- 長所: 最も安全・単純。
- 短所: 「夜間セルフ改善」の狙い（放っておくと安全な改善が溜まる）を実現できない。

## Consequences（結果）

- 得るもの:
  - 毎晩、無害な改善が自動で計画され、承認済み項目は自動で PR 化される。人はレビューとマージに集中できる。
  - 計画イシューが肥大化せず、板として使い続けられる。
  - 自動化の各段（M/A/P・Execute・マージ）に明確な安全境界が引かれる。
- 失うもの / コスト:
  - cron Routine の運用管理（起動確認・失敗時の通知）。
  - 無人 Execute のため、consult 項目は自動では進まない（意図した安全側の制限）。
  - **既知の制約**: 無人（headless）で起動する cron セッションでは、対話認証系の MCP（GitHub 等）が
    利用できない場合がある。その場合、夜間 M/A/P はスクリプト実行と knowledge コミットまでを行い、
    イシュー掲示は MCP が使える次の対話セッションへ委ねる（デグレード動作）。初回起動後に要確認。
- **再検討のトリガー**:
  - 計画イシューが1本で収まらなくなったら「1項目=1イシュー」へ移行する新 ADR を検討する。
  - サーキットブレーカーが頻発、または無人 Execute の PR 品質が低いなら、自動 Execute を停止し手動へ戻す。
  - 即時性が必要になったら `issues.edited` Webhook 即時 Execute を新 ADR で導入する。
  - headless での MCP 不可が恒常的な障害になるなら、投稿経路（API トークン等）を新 ADR で見直す。
