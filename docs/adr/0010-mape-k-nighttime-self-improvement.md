# 0010: MAPE-K 型の夜間セルフ改善システム

- Status: Proposed
- Date: 2026-07-19
- Deciders: nigoh, Claude

## Context（背景）

土台（deb）を使い続ける中で「小さな改善（テスト追加・整形・ドキュメント同期・軽微なリファクタ）」が
溜まっていくが、日中の集中作業では後回しになりがちである。一方で、リポジトリの状態観測と改善案の立案は
**読み取り中心で安全・低コスト**であり、夜間に自動で回せる。危険なのは「実際に変更を加える実装」だけである。

そこで、自律計算の古典的アーキテクチャ **MAPE-K**（Monitor / Analyze / Plan / Execute ＋ 共有 Knowledge）に沿って、
「安く読んで考える」フェーズ（M/A/P）と「高コストで壊しうる」フェーズ（E）を分離し、
**人間の承認ゲート**を GitHub イシューのチェックリストとして挟む仕組みを土台に組み込む。

制約:
- 本リポジトリはスタック非依存の土台であり（ADR-0003）、実体は Bash + steering + ドキュメントである。
  よって MAPE-K も同じ流儀（Bash 決定論スクリプト ＋ Claude 起動スキル）で実装する。
- 絶対原則（ADR-0004）を破らない: main 直接変更禁止・トピックブランチ + PR・品質ゲートは check.sh 単一入口。

## Decision（決定）

MAPE-K 型の夜間セルフ改善システムを、以下の責務分離で土台に組み込む。

1. **K（共有ナレッジ）** を `knowledge/`（人が読める Markdown）に置く: `BACKLOG.md` / `PROGRESS.md` /
   `POLICY.md` / `HEALTH.md`。全フェーズがここを読み書きし、周回ごとに判断が良くなる「記憶」とする。
2. **M / A / P は決定論的な Bash スクリプト**（`mape/monitor.sh` / `analyze.sh` / `plan.sh`、統合 `mape/run.sh`）
   として実装する。読み取り専用・低コストで、夜通し何度でも回してよい。出力は `mape/state/` の中間成果物
   （gitignore せず、証跡として残す）と `knowledge/` の更新。
3. **P は GitHub イシューにリスク3分類のチェックリスト**を掲示する（`mape/plan.sh` が本文を生成し、
   スキルが MCP で投稿/更新する）。分類は **自動 / 承認 / 相談**:
   - **自動**（無害・可逆: 整形・テスト追加・パッチ更新・ドキュメント同期）→ チェック不要で実装。ただし PR まで（マージしない）。
   - **承認**（挙動が変わる: 新機能・リファクタ）→ ユーザーがチェックした項目だけ実装。
   - **相談**（認証・課金・データ・秘密・デプロイに触れる）→ チェックされても即実装せず、まず質問する。
4. **E（実行）は Claude 起動スキル**（`.claude/skills/mape-execute`）とし、**ポーリング型**でイシューを読み、
   「チェック済み・未着手」の項目を **1周1件** だけ安全なループで実装する。テスト緑→ブランチ + PR、
   赤→変更破棄して失敗を記録。冪等性はイシューのチェック＋「PR #N で対応」コメントで担保する。
5. **ガードレール**を明示する: 1周1件・ブランチ + PR・main を直接触らない・本番/秘密/課金に触れない・
   **サーキットブレーカー**（同一テストの連続失敗や revert 連続で Execute を停止し通知）・
   **冪等性**（二重実行防止）・**自動アーカイブ**（未チェックのまま一定期間過ぎた計画項目を腐らせない）。

夜間の周回起動は `.claude/skills/mape-night`（M→A→P を回してイシューを更新）とし、初手はポーリング型、
`issues.edited` Webhook による即時化は将来拡張とする。

## Options Considered（検討した選択肢）

### 案1: MAPE-K（Bash 決定論スクリプト M/A/P ＋ Claude スキル E ＋ 承認ゲートを GitHub イシュー）（採用案）

- 長所:
  - 「安く読んで考える」と「高コストで壊しうる」の分離が構造として明快（コスト・リスク上限を E 側に集約）。
  - M/A/P が決定論スクリプトなので `check.sh` の自己テストで機械検証でき、再現性がある。
  - 承認ゲートが GitHub イシューのチェックボックスなので、人間の関与コストが最小（見て、チェックするだけ）。
  - 土台の既存流儀（Bash + steering + トレーサビリティ）と一貫し、スタック非依存を保てる（ADR-0003）。
- 短所:
  - 分析の「賢さ」を決定論ヒューリスティクスに寄せる分、初期は素朴（Knowledge の蓄積で漸進改善する前提）。
  - 複数リポジトリ・複数言語への一般化は追加作業（本 ADR の対象はこの土台リポジトリ自身）。

### 案2: 単一の Claude スキルが M〜E をすべて対話的に実行する

- 長所: 実装が単純。分析にフル LLM の柔軟性を使える。
- 短所:
  - 決定論部分（監視・計画）まで LLM に委ねると再現性・機械検証性が下がり、`check.sh` で守れない。
  - 「読むだけの安全フェーズ」と「壊しうる実行フェーズ」の分離が曖昧になり、コスト/リスク上限を置きにくい。
  - 承認ゲートが対話に埋もれ、人間が「夜間の提案を朝に一覧で見てチェックする」体験にならない。

### 案3: GitHub Actions（cron）＋外部オーケストレーターで実装する

- 長所: スケジュール実行が OS/CI ネイティブ。
- 短所:
  - 土台をスタック非依存に保つ方針（ADR-0003）に反し、CI に個別ロジックを直書きすることになる（ADR-0004 違反）。
  - Claude Code の steering 資産（skills/agents/hooks）を活かせず、実行環境が二重化する。

## Consequences（結果）

- 得るもの:
  - 夜間に無害な改善案が GitHub イシューへ自動で溜まり、人間はチェックするだけで安全に実装が進む。
  - `HEALTH.md` の指標を周回ごとに記録するため「N 周で TODO 12→3」のように改善を定量化できる。
  - `POLICY.md` に却下理由が蓄積し、A が提案前に必ず読むことで、好みに寄り却下される提案が減っていく。
- 失うもの / コスト:
  - 決定論ヒューリスティクスの保守コスト（新しい症状の型を増やすたびに analyze.sh を拡張）。
  - Knowledge ファイルが周回で育つ前提のため、初期数周は提案の質が素朴。
- **再検討のトリガー**:
  - 対象が複数リポジトリ/複数スタックに広がったら、一般化のための新 ADR を検討する。
  - ポーリングの遅延が問題になったら `issues.edited` Webhook 即時化を新 ADR で導入する。
  - サーキットブレーカーが頻発する（＝提案の質が低い）なら、Analyze の設計を見直す新 ADR を検討する。
