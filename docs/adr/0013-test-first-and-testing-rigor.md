# 0013: テスト厳格度ポリシー（test-first を含む）を重要度×規模で校正する

- Status: Proposed
- Date: 2026-07-21
- Deciders: （PR レビュアー）

## Context（背景）

「実装方法として TDD を採用したいがどうか」という問いを、リポジトリの現状・実データ・
性質に照らして多観点（現状把握・適合性/エビデンス・導入設計・敵対的批判・反対案）で検証した。
判明した事実:

- **red→green は既に存在するが「バグ回帰の再発防止」限定**（ADR-0007 / `verification.md` 予防活動の
  「障害からの再発防止」項 / `test-engineer.md` / `fix`/`postmortem` スキル）。バグ起点でない**新規実装の
  test-first は規約の空白**。
  この決定が触るのは ADR-0007 の red→green の適用範囲であり、ADR-0005 の V字（成果物⇄検証レベルの
  対応であって時間順の強制ではない）とは矛盾しない。
- **実バグの所在**: 10 ラウンドのバグハントで確定した 36 件のうち約 34 件は locale・ツール欠落・
  破損入力・並列・ガードバイパス等の「思いつかなかった入力」で、example-first の TDD では構造的に
  届かない。効いたのは敵対的探索＋property テスト＋レビュー（`knowledge/insights/2026-07-20-bug-hunt.md`）。
  一方、push ガードの取りこぼし約7件は一塊で、ガードの**契約/表テストを先に書けば**列挙規律で拾えた。
- **AI 実装者の最大リスクは false-green**（自信満々の誤コードが、実装後に同じエージェントが書いた
  “それらしい”テストを通ってしまう）。これを塞ぐ唯一の安価な機構が「**赤を実際に観測してから緑にする**」
  ＝ test-first の falsification。ここが現状に無い本当の穴。
- **機構的制約**: Stop フック（`.claude/hooks/quality-gate.sh`）が未コミット変更時に `check.sh` の
  全緑を要求するため、**赤を残したまま別ターン/別エージェントへ handoff できない**。red→green は
  1セッション内で連続して行い、緑で1コミットする。
- **強制の分界**: 「赤を先に観測したか」という**順序は自律エージェントには検証不能**（テストは緑に
  書けるし、後から赤を演出できる）。機械強制できるのは**結果**（要件被覆＝`check-traceability.sh`、
  スタック導入後のテスト緑・網羅率＝`check.sh` への追加）のみ。ADR-0004（弱めない・単一入口）を守る。
- リポジトリの土台には既に 21 本のシェルスクリプトと純粋ロジック（`mape/*` の score/classify 等）と
  そのユニットテスト（`mape/tests/`）があり、**土台自身が第一のテスト対象**（「土台はほぼ非テスト対象」
  ではない）。

## Decision（決定）

**「TDD 一律」ではなく、既存の 2 軸テーラリング（重要度×規模、`lifecycle.md`）に「テスト厳格度」を
足す。** その一戦術として test-first を、効く所に絞って標準化する:

1. **test-first（赤を実行して観測 → 最小実装で緑 → refactor）** を、**純粋ロジック関数**と
   **重要度「高」**（認証・課金・個人情報・マイグレーション・公開 API）に適用する。バグ回帰の
   既存 red→green はこの一般形の一事例と位置づける。**red→green は 1 セッション内で連続**して行い、
   赤はトランスクリプトに残し、緑で 1 コミットする（Stop フック制約）。
2. **ガード等の高重要度コンポーネントは契約/表テストを先に書く**（「保護 ref に届く全 push 形は
   ブロック」のように振る舞いの契約を列挙してから実装/修正する）。
3. **エッジ多発コード**（パーサ・locale/`date`/`sort`・ツール依存・並列・ガード）は
   **敵対的/property テストを必須**とする（`/test-design` の境界値・直交表・状態遷移＋ `bug-hunt`）。
   リポジトリの欠陥はここに集中するため、test-first より優先度が高い。
4. **順序（red-first）は文化的規律**に留める（機械強制しない＝偽装しない）。**機械強制は結果側**
   （要件被覆 100%＝`check-traceability.sh`、スタック導入後のテスト緑・網羅率閾値＝`/stack-init` が
   `check.sh` へ追記）に限定する。既存ゲートを弱めない・迂回しない（追加のみ。ADR-0004）。
5. **テーラリング準拠**: 自明変更・重要度低は test-first を省略してよい。重要度「高」は規模が小でも
   省略しない（既存の「重要度が省略を上書きする」原則をそのまま適用）。省略時は PR/イシューに理由を1行残す。

## Options Considered（検討した選択肢）

### 案1: テスト厳格度ポリシーとして採用（採用）

test-first を「純粋ロジック＋重要度高」に、契約テストを「ガード」に、敵対的/property テストを
「エッジ多発コード」に割り当て、既存テーラリング表の1セルとして機械強制できる形で足す。

- 長所: リポジトリの実欠陥プロファイル（敵対的入力が支配的）と AI の false-green リスクの双方に整合。
  既存機構（段階ゲート・テーラリング・traceability・単一ゲート・ADR-0007 の予防/検知）に相乗りし、
  外来のプラクティスを憲法に押し付けない。強制可能な部分（結果）だけを機械化し、不能な部分（順序）を
  偽装しない誠実さ。最小差分（ADR 1・rule 1・既存文書の一般化）。
- 短所: test-first の「順序」は信頼ベースに留まる（原理的限界）。ポリシーが複合的で、運用側が
  「どの戦術をいつ」を判断する必要がある（テーラリング表で軽減）。

### 案2: 素直な TDD を全面採用（不採用）

新規実装も含め red→green→refactor を非自明コード一律に必須化する。

- 長所: falsification（真の赤）と均一な小刻みリズムを最大化（Fucci らの「粒度と均一性が効く」に整合）。
  テスト容易な設計への圧力を常時かけられる。
- 短所: **テーラリング（重要度×規模）という憲法（ADR-0005）と正面衝突**。リポジトリの大半を占める
  markdown/ADR/glue や自明変更に example-first のセレモニーを撒き、欠陥 ROI が最低の所にコストを払う。
  実データ上、支配的欠陥（敵対的入力）には届かない。

### 案3: 採用せず現状維持（不採用）

red→green はバグ回帰限定のまま。敵対的/property テスト＋レビューに投資する。

- 長所: 実データに最も忠実（バグは敵対的探索で見つかった）。`/spec` 受入基準＋`/test-design`＋
  traceability で前倒しは既に担保。ゲートは既に test-after を機械強制している。
- 短所: **AI が書くコードの false-green を塞げない**（実装後に同エージェントが書くテストは実装の
  挙動を写しがち。traceability は「テストの存在」は見るが「誤実装に対して落ちるか」は見ない）。
  この穴は限定的だが AI 実装リポジトリでは小さくない。

## Consequences（結果）

- 得るもの: AI 実装の false-green を「純粋ロジック＋重要度高」で赤の観測により塞ぐ。ガードの契約テスト
  先行で取りこぼしクラスタの列挙規律を得る。エッジ多発コードの敵対的/property テストを必須化して実欠陥
  クラスを継続的に捕捉。既存 red→green 記述を新規ロジックへ統一。憲法（テーラリング/単一ゲート）と非衝突。
- 失うもの: test-first の順序は機械保証されない（信頼ベース）。自明変更の速度低下はテーラリングで相殺。
- **再検討のトリガー**:
  - red-first 順序を軽量かつ堅牢に機械検証する手段が現れたら、機械強制への格上げを検討する。
  - test-first の逸脱に起因する欠陥が `/postmortem` で反復したら規律を強化する。
  - 逆に、test-first のセレモニーが欠陥 ROI に見合わない（自明変更の摩擦だけが残る）と観測されたら
    適用範囲を縮小する。
