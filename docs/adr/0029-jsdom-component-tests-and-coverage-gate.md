# 0029: UI コンポーネントテスト（jsdom）と網羅率ゲートを導入する

- Status: Proposed
- Date: 2026-08-14
- Deciders: リポジトリオーナー / Claude

## Context（背景）

これまで UI の検証は Playwright の E2E だけだった。E2E は導線の回帰には強いが、
コンポーネント単位の分岐（選択状態の描画・コールバックの発火・境界の表示）を網羅するには
1 ケースが重すぎる。また品質ゲートはテストの緑/赤しか見ておらず、テストされていない領域が
増えても検知できない（BACKLOG に P2/P3 として積まれていた 2 項目）。

## Decision（決定）

1. **jsdom + Testing Library を導入し、コンポーネントテストを Vitest で書けるようにする。**
   既定のテスト環境は node のままとし、コンポーネントテストのファイル先頭に
   `@vitest-environment jsdom` プラグマを書いて切り替える（純粋ロジックのテストを遅くしない）。
2. **網羅率ゲートを check.sh に追加する。** `vitest run --coverage`（V8 プロバイダ）で
   `src/lib/**` に閾値（lines/statements/functions 90・branches 85。導入時実測
   95.7/94.8/98.6/85.5 を下回らない水準）を課す。閾値を下げる変更は品質ゲートの弱体化として
   扱う（ADR-0004）。UI 層は E2E とコンポーネントテストで見るため数値ゲートの対象にしない。
   `src/lib/use*.ts`（React フックが lib に残る既存の層例外）は UI 側とみなして除外する。

## Options Considered（検討した選択肢）

### 案1: jsdom プラグマ切替 + lib 限定の網羅率ゲート（採用）

- 長所: 既存のロジックテストは node 環境のまま高速。ゲートは「純粋ロジックは測れる・測る」領域に
  限定され、閾値が意味を持つ。導入コストが小さい
- 短所: UI 層の網羅率は数値化されない（E2E とコンポーネントテストの定性被覆に留まる）

### 案2: 全ファイル jsdom + 全体網羅率ゲート

- 長所: 設定が一律で単純。アプリ全体の網羅率が一目で分かる
- 短所: ロジックテストまで jsdom で遅くなる。UI 込みの網羅率は分母が大きく閾値が形骸化しやすい
  （下げ圧力がかかり ADR-0004 と衝突する）

### 案3: 現状維持（E2E のみ）

- 長所: 追加依存なし
- 短所: コンポーネント分岐の回帰が E2E の網の目をすり抜ける。BACKLOG の指摘が放置される

## Consequences（結果）

- 得られるもの: コンポーネント単位の回帰検知、`src/lib` の網羅率の見える化と下限保証
- 失うもの: devDependencies の増加（jsdom / @testing-library/react / @vitest/coverage-v8）
- **再検討のトリガー**: UI 層のバグが E2E・コンポーネントテストの両方をすり抜ける事例が出たら
  UI 層の数値ゲート化を再検討する。閾値が開発を常態的に阻害するなら水準を ADR で見直す
