# 0023: MAPE-K の夜間 cron を止め、手動起動のみにする（ADR-0019 を supersede）

- Status: Proposed
- Date: 2026-08-01
- Deciders: （リポジトリオーナー・PR レビュアー）
- Supersedes: ADR-0019（MAPE-K の夜間自走（heartbeat）— GHA cron で決定論 M→A→P）

## Context（背景）

ADR-0019 で `mape-nightly.yml` に `cron: '19 17 * * *'` を置き、毎晩 M→A→P を実走させた。
狙いは2つあった。**(a)** HEALTH の推移を刻むこと、**(b)** 周回が止まったら次の周回が「ループ休眠」を
自己検知すること（ADR-0014 が「核心的欠陥」と呼んだ状態への対策）。

7日運用した実測が出たので、狙いが達成されたかを確かめた。

### 実測1: 6日間で新しく分かったことは3行だけだった

7/25 と 7/31 の `mape/state/proposals.tsv` を差分で比べた結果:

| 変化 | 中身 |
|---|---|
| 1 | 「MAPE ループが 168 時間 休眠 — 夜間 cron が回っていない可能性」 |
| 2 | 品質ゲートの実行時間 160s → 241s |
| 3 | churn 首位が `mape/tests/run.sh` → `docs/adr/README.md` |

**残り13件の提案は6日間まったく同一。** 1行目は後述のとおり自分の失敗の自己申告であり、
実質の新情報は2行目（gate_s）だけだった。

### 実測2: 解決済みの提案が6晩 P1 に残り続けた

```
consult P1 5 3 15  LICENSE を追加（土台なのに不在＝再利用が法的に不成立。選定は要判断）
```

LICENSE は ADR-0012 で MIT に決定済みで、リポジトリ直下に存在する。
**解決済みの提案が消えずに毎晩上位に出続けていた。** 毎晩回すほど、この誤りが目に触れる回数が増える。

### 実測3: PR が作れず、失敗ブランチだけが溜まった

```
pull request create failed: GraphQL: GitHub Actions is not permitted to
create or approve pull requests (createPullRequest)
```

7/26 から 7/31 まで**6日連続で失敗**。push は毎晩成功していたため、`chore/mape-cycle-*` ブランチが
7本溜まり、中身は誰の目にも触れなかった。リポジトリ設定（Allow GitHub Actions to create and approve
pull requests）で直せるが、直したところで実測1・2の状況は変わらない。

### 実測4: Execute は設計上ずっと抑止されていた

夜間ジョブは `main` 上で走るため `safe-state` が必ず 0 になり、`Execute を抑止（保護ブランチ上（main））`
が毎回記録されていた。**ADR-0011 が想定した「毎晩 auto/approve を1件実装する」運用は一度も起きていない。**

## Decision（決定）

**`mape-nightly.yml` から `schedule:` を削除し、`workflow_dispatch` による手動起動のみにする。**

- ワークフローとスクリプト（`mape/`）・スキル（`/mape`）は**削除しない**。周回の中身は変えない
- トレンドが必要なときは**ラウンド開始時に手で1回**まわす（Actions の Run workflow か `/mape night`）
- `knowledge/POLICY.md` の運用モードを「手動で1周」に書き換える

### なぜ「削除」ではなく「手動化」か

`gate_s` の推移（4s → 173s → 241s）は毎回走らないと取れない情報で、**実際に効いている**
（品質ゲートが60倍に肥大し、1回の実行が体感10分に達している）。この観測口は残す価値がある。
一方その頻度は「毎晩」である必要がなく、**変更が起きたとき＝ラウンドの節目**で十分である。

### ADR-0019 の狙い (b) の扱い

「周回が止まったら次の周回が休眠を検知する」機構は、**手動運用では意味を失う**（手で回さない限り
検知も走らないため、検知はトートロジーになる）。実際、実測1の1行目がまさにその空回りだった。
休眠検知のコード自体は残すが、**それを自動運用の根拠にはしない**。

## Alternatives（検討した代替案）

| 案 | 却下理由 |
|---|---|
| リポジトリ設定を直して夜間 cron を続ける | PR は作れるようになるが、実測1・2（新情報が gate_s だけ・解決済み提案の残留）は変わらない。毎晩レビュー対象が1本増えるだけ |
| 週1に落とす | 頻度の問題ではなく「変更が無い日に回しても新情報が出ない」構造の問題。ラウンドの節目に回すほうが情報密度が高い |
| PR をやめて計画イシューへのコメント更新だけにする | 権限エラーとブランチ蓄積は消えるが、`knowledge/` の証跡（HEALTH の推移）がコミットされず、トレンドが残らない。目的 (a) を失う |
| ワークフローごと削除する | `gate_s` の観測口を失う。手動起動なら維持コストはほぼゼロ |
| 提案の陳腐化（実測2）を直してから判断する | 直すべき欠陥ではあるが、直しても実測1（提案が変わらない）は変わらない。別課題として切り出す |

## Consequences（結果）

**良くなること**

- 毎晩の失敗通知と `chore/mape-cycle-*` ブランチの蓄積が止まる
- 提案リストを見るタイミングが「変更があった直後」に揃い、情報密度が上がる
- リポジトリ設定（Actions の PR 作成許可）を変えずに済む — 権限は絞ったままにできる

**失うもの / 負担になること**

- HEALTH の時系列が**手で回した回数分しか刻まれない**（自動の毎日1点は無くなる）
- 回し忘れると観測が途切れる。ADR-0019 の「休眠の自己検知」は上記のとおり手動運用では効かないので、
  **回すのはラウンド運用（`/round`）の規律に委ねる**

**再検討のトリガー**

- 手動運用で数ラウンド回した結果、観測が途切れて `gate_s` の劣化に気づけなかったとき
- MAPE-K の提案が「毎回変わる」ようになったとき（＝自動で回す情報価値が生まれたとき）
- `safe-state` の判定が変わり、無人 Execute が実際に動く構成になったとき

## Follow-up（この ADR では扱わない課題）

- **解決済み提案が残り続ける欠陥**（実測2）— `mape/analyze.sh` のゾンビ提案対策は別課題として起票する
- 溜まった `chore/mape-cycle-*` ブランチ7本の削除（オーナー操作）
