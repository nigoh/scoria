# 0022: ドキュメント構成をピラミッド原則で統一し、構造マーカーで機械検査する

- Status: Proposed
- Date: 2026-08-01
- Deciders: （PR レビュアー）

## Context（背景）

ADR-0021 でドキュメントサイトを3層（`index.html` / `guide.html` / `reference.html`）に分けたが、
利用者から「読んでも分からない」という具体的な指摘を受けた（イシュー #50）:

1. `Dev environment base` が何の略で何なのかが冒頭に無い
2. ADR・steering・fail-closed などの専門用語が注釈なしで出る
3. 「テンプレートとして複製する」が GitHub を知らない読者に伝わらない
4. 「日常の開発」のような動きのある概念が静止した文章でしか説明されていない
5. README が長く、サイトとの役割分担が曖昧
6. 文書構成の原理が無く、節ごとに書き味が違う
7. 図が少なく、文章から入るので理解に時間がかかる

これは個々の文言の問題ではなく、**文書の構成に原理が無い**ことの症状である。原理を決めても、
このリポジトリの他の規約と同じく「文章で書いただけの規約は静かに形骸化する」（ADR-0004 の3層強制の前提）。

制約:

- ADR-0003（土台はスタック非依存）— 静的サイトジェネレータのような依存を持ち込みたくない
- ADR-0004（品質ゲートの単一入口・ゲートを弱めない）
- ADR-0021（`reference.html` は生成物。手で編集しない）
- 気づきカード #40（Round 9）— 任意ツールの有無で判定が変わる状態を作らない。判定不能は安全側に倒す

## Decision（決定）

**バーバラ・ミントのピラミッド原則をこのリポジトリの文書の強い規約とし、
機械判定できる部分を構造マーカーの検査として品質ゲートに組み込む。**

### 1. 構成の原理はピラミッド原則に統一する

規約は `.claude/rules/docs.md`（`paths:` で HTML / README / `docs/**` / `build-docs.sh` にスコープ）。

- **結論 → 根拠 → 詳細**。見出しは読者の問い、その直後に答えを置く
- **結論は1文**（1文にまとまらないなら節を割る）
- 同階層は MECE、並べる順の原理は1つに統一する
- 見出し階層を飛ばさない

### 2. 「図が先、文が後」を構成規約に含める

節の中では結論の直後に `<figure>` を置き、文章はその補足とする。視覚的に掴んでから文で確かめる順にする。
動きのある概念（複製の手順・開発サイクル）は **CSS アニメーション**で見せる。ただし
**アニメーションを唯一の情報経路にしない**（静止状態でも同じ情報が読める）。
`@keyframes` を使うファイルには `prefers-reduced-motion` の指定を必須とする。

### 3. 用語は初出だけ注釈する

`<abbr title="1行の定義">` または `class="term"` を持つ要素で囲む。**初出のみ**必須（全出現に付けると読めない）。
除外領域（`<head>` / `<script>` / `<style>` / `<code>` / `<pre>` / `<kbd>` / `<samp>` / `<nav>` / `<footer>` /
`<svg>` / 見出し / 用語集自身 / 属性値 / HTML コメント / 語の一部）を規約に明示し、誤検知で執筆が窮屈にならないようにする。

### 4. README は入口だけにする

README は「deb が何か・どこを読むか・最短の始め方」に絞る（125行 → 約40行）。深い説明はサイトに置く。
README を読む人とサイトを読む人で情報が二重管理になるのを避ける。

### 5. 機械検査するもの / しないもの を明示的に線引きする

`scripts/check-docs-structure.sh` を `scripts/check.sh` に配線する（gate ⑤）。検査するのは
**構造マーカーで決定可能なものだけ**:

| # | 検査 |
|---|---|
| 0 | 用語集の正本が規約と検査スクリプトで一致する |
| 1 | 見出しを持つ `<section>` は見出しの直後が `<p class="answer">` |
| 2 | 結論は1文（句点は1つまで）かつ空でない |
| 3 | 見出し階層を飛ばさない |
| 4 | 見出しブロックに図があるなら、最初の `<figure>` は最初の本文段落より前 |
| 5 | 用語集の語の初出に注釈がある |
| 6 | `@keyframes` を使うファイルに `prefers-reduced-motion` がある |

**機械検査しないもの**（規約に明記し、人のレビュー = doc-auditor に委ねる）: MECE か・根拠の並べ方の
原理が統一されているか・上の階層が下の要約になっているか・図の内容と本文が一致しているか・
README / `docs/` の Markdown。意味の判断を機械が装うと、通ったことが品質の証明だと誤解される。

検査スクリプト自身の動作テスト `scripts/test-docs-structure.sh`（検査項目ごとに正常系と異常系を対で持つ）も
配線する。`build-plugin.sh --check` / `build-docs.sh --check` と同じパターン。

### 6. 用語集は正本を1つにし、二重管理を機械で塞ぐ

用語集は規約（`.claude/rules/docs.md`）と検査スクリプトの両方に必要になる。片方だけ増やすと
「規約には書いたが検査されない語」が生まれるので、**両者の一致自体を検査0にする**
（`check-skill-sync.sh` と同じ「一覧と実体の同期」パターン）。

### 7. 生成物のマーカーは生成器側に入れる

`reference.html` は生成物なので手で直さない（ADR-0021）。結論段落・用語注釈は
`scripts/build-docs.sh` のテンプレート側で出力する。

### 8. gawk 不在は fail-closed

HTML の構造判定には gawk が要る。無い環境では「判定不能」を合格に倒さず、明示メッセージで非ゼロ終了する
（ADR-0021 の §3 と同じ扱い。気づきカード #40）。

## Alternatives（検討した代替案）

| 案 | 却下理由 |
|---|---|
| 規約を文章で書くだけ（機械検査しない） | ADR-0004 の前提どおり、強制されない規約は摩耗する。実際に7つの指摘はすべて「原理が無い」ことの結果 |
| MECE や「上位が下位の要約か」まで機械判定する | 意味の判断であり決定不能。無理に近似すると誤検知で執筆が歪み、通過が品質の証明だと誤解される |
| Markdown を正本にして静的サイトジェネレータで HTML を作る | ADR-0003 / 0021 に反して土台に依存を増やす。現行は依存ゼロの自前レンダラで足りている |
| 用語を全出現で注釈する | 読めなくなる。初出のみで十分（用語集への導線は別に置く） |
| アニメーションだけで手順を説明する | reduced-motion 利用者・静止画像で読む人に情報が届かない。アニメーションは補助に限る |
| 用語集を検査スクリプトだけに持つ | 規約を読んだだけでは何が検査されるか分からない。逆に規約だけに持つと awk から読む処理が増えて壊れやすい。両持ち＋一致検査を選んだ |

## Consequences（結果）

**良くなること**

- 節を書くときに「この節の結論は1文で何か」を必ず考えることになる（構成の質が書き手に依存しなくなる）
- 用語の初出注釈が漏れたら CI が落ちるので、読者にとっての初見の壁が構造的に減る
- README とサイトの役割分担が固定され、二重管理が減る

**負担になること**

- HTML を書くときに構造マーカー（`<p class="answer">` / `</p>` の省略禁止）の制約が増える
- 用語を増やすときは規約と検査スクリプトの両方を直す必要がある（一致は検査0が保証する）
- 図を増やすと SVG の保守コストが増える（依存を増やさない代償）

**再検討のトリガー**

- 構造マーカーの誤検知で執筆が回避的になったとき（除外規則を足すか、その検査を人のレビューへ戻す）
- Markdown の分量がサイトを上回ったとき（Markdown 側の機械検査を改めて検討する）
