# 0009: テンプレート由来リポジトリから本家へのフィードバックループ

- Status: Accepted
- Date: 2026-07-18
- Deciders: リポジトリオーナー

## Context（背景）

deb はテンプレート複製（ADR-0003）やコンパニオンプラグイン（ADR-0008）で各リポジトリへ広がる。
現場で使ううちに「あった方がいい機能」「プロセスの摩擦」「再利用できる気づき」が生まれるが、
それらは各リポジトリに閉じてしまい、**土台（本家 deb）が改善の機会を受け取れない**。
deb には既に「気づきカード → 規約反映」（ADR-0002）があるが、これは同一リポジトリ内の学習ループである。
これをリポジトリを越えて downstream → base に拡張したい。

## Decision（決定）

**本家 deb への上流フィードバックループを設ける。**

- **`/feedback` スキル**: 現場の気づき（機能要望・摩擦/不具合・再利用できる気づき）を定型に整形し、
  **人間の確認を経てから**本家リポジトリ（`nigoh/deb`。fork した場合は自リポジトリに変更可）へ
  イシューを起票する。GitHub ツールが使えない場合は事前入力済みの「新規イシュー URL」を提示する。
  このスキルは移植可能サブセットに含める（テンプレート由来・プラグイン導入の双方で使える。ADR-0008）。
- **本家のイシューテンプレート＋ラベル**: `.github/ISSUE_TEMPLATE/template-feedback.yml`（種別・
  内容（何を・なぜ・どう改善したいか）・関係する機構/段階・deb のバージョン）と `template-feedback` ラベル。
- **振り返りと接続**: `/round close` の振り返りで、土台（deb 自身）に効く気づきは `/feedback` で本家へ送る。
- **安全弁**: フィードバックは外向きの発信であり、送信前に必ず内容を提示して確認する。アプリ固有の情報・
  秘密情報を含めず、deb（土台）に関する内容に限定する。

## Options Considered（検討した選択肢）

### 案1: /feedback スキル＋本家イシューテンプレート（採用）

- 長所: 現場の文脈のまま整形して本家に届く。プラグインにも載せられる。既存の気づきカード文化と地続き
- 短所: 上流リポジトリ ID をスキルに持つ（fork 時は要変更 → スキルに明記）

### 案2: ドキュメントで「本家に issue を立ててください」と案内するだけ

- 長所: 実装ゼロ
- 短所: 摩擦が高く、実際にはフィードバックされない。整形もされない

### 案3: 自動テレメトリ

- 長所: 手間なく集まる
- 短所: プライバシー・秘密情報の懸念。土台の思想（明示・確認）に反する。過剰

## Consequences（結果）

- 本家 deb が現場の改善要求を継続的に受け取れる（テンプレートのブラッシュアップが回る）
- `/feedback` は外向き発信のため確認を必須にする（誤送信・情報漏れの防止）
- **再検討のトリガー**: フィードバックが増えて手動整理が律速になったら、ラベル運用や集約を見直す
