# 0006: 要件管理とトレーサビリティを ID 体系で徹底する

- Status: Accepted
- Date: 2026-07-17
- Deciders: リポジトリオーナー

## Context（背景）

IPA/SEC「高信頼化ソフトウェアのための開発手法ガイドブック」は、品質機能展開（QFD）に基づく
**トレーサビリティ管理**（顧客要件 → 要求品質 → 設計 → 実装 → テストの一貫した追跡）を、
高信頼ソフトウェアの中核手法として挙げている。また共通フレームは「要件の合意及び変更ルールの
事前確立」「非機能要件の重視」を提唱する。deb にこれを翻訳して取り込む。

## Decision（決定）

要件を ID で管理し、設計・実装・テストへ一貫して追跡する。

**ID 体系**（`docs/process/traceability.md` が正本）:
- `REQ-<領域>-<連番>` 機能要件 / `NFR-<分類>-<連番>` 非機能要件
- `DES-<連番>` 設計判断（ADR に昇格しうるもの）
- `TEST-<レベル>-<連番>` テストケース（レベル: unit/integration/system/acceptance）

**規律**:
- すべての機能要件・非機能要件は受入基準（Acceptance Criteria）を持つ
- すべての要件は、それを検証する TEST を最低1つ持つ（トレーサビリティの完全性）
- 要件の追加・変更は変更管理ルール（`docs/process/requirements.md`）に従い、合意を記録する
- 非機能要件（NFR）は既定の7カテゴリ（性能・効率性／信頼性／使用性／セキュリティ／保守性／移植性／運用性。正本は `docs/process/requirements.md`）を必ず一巡して検討する

**機械検証**: `scripts/check-traceability.sh` が「全 REQ/NFR に対応 TEST があるか」「要件に受入基準があるか」を
検査し、`scripts/check.sh` から呼ぶ（品質ゲート化）。要件ドキュメントが存在しないリポジトリ（土台の初期状態）では
このゲートは何もしない（スタック導入後・要件定義後に有効化される）。

## Options Considered（検討した選択肢）

### 案1: ID 体系＋トレーサビリティの機械検証（採用）

- 長所: 要件の検証漏れが機械的に検出できる。変更影響の追跡が可能。IPA の QFD 手法と整合
- 短所: ID 付与の運用コスト（→ `/spec` スキルが採番を自動化して緩和）

### 案2: 自然言語の要件のみ（ID なし）

- 長所: 手軽
- 短所: 要件とテストの対応が人手頼みで、抜けが検出できない

## Consequences（結果）

- 要件定義成果物（`docs/requirements/`）が V字の起点になり、段階ゲート（ADR-0005）と接続する
- 変更管理が明文化され、要件の勝手な追加・削除が規約違反として検出できる
- **再検討のトリガー**: ID 運用が過重なら、粒度を粗く（機能単位のみ）テーラリングする
