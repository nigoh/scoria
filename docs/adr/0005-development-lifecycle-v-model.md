# 0005: 開発ライフサイクルとして V字モデル＋段階ゲートを採用する

- Status: Accepted
- Date: 2026-07-17
- Deciders: リポジトリオーナー

## Context（背景）

deb は開発規約とラウンド運用（ADR-0002）を持つが、「どの順で・何を作り・どこで検証するか」という
開発ライフサイクルそのものは未定義だった。IPA/SEC「ソフトウェア開発の標準プロセス」（共通フレーム/SLCP）は、
超上流（企画・要件定義）の重視、V字モデル（各設計成果物に対応する検証レベル）、運用・保守を含めた
ライフサイクル思考を提唱している。これらを Claude Code の土台に翻訳して取り込む。

## Decision（決定）

開発ライフサイクルを **企画 → 要件定義 → 設計 → 実装 → 各レベルのテスト → 運用・保守** とし、
**V字モデル**で左辺（要件・設計）と右辺（検証）を対応づける:

| 左辺（作り込み） | 右辺（検証） | 対応 ID |
|---|---|---|
| 要件定義（機能・非機能・受入基準） | 受入テスト / 妥当性確認 | REQ ⇄ TEST(acceptance) |
| 基本設計 | システムテスト | DES ⇄ TEST(system) |
| 詳細設計 | 結合テスト | DES ⇄ TEST(integration) |
| 実装 | 単体テスト | code ⇄ TEST(unit) |

各ラウンド（ADR-0002）は上記の段階を通す。段階の移行には**段階ゲート**を置く:
前段の成果物と受入基準が揃い、対応する検証が緑であることを確認してから次段へ進む。
プロセスの詳細は `docs/process/` に置き、`/round` と `/stack-init` から参照する。

テーラリング（共通フレームの修整）: 変更の規模に応じて段階を省略してよい。自明な修正は
要件定義・設計を省き実装＋テストのみでよい（ADR-0002 の「自明な修正は直接実装」と整合）。
省略の判断は `docs/process/lifecycle.md` の基準に従う。

## Options Considered（検討した選択肢）

### 案1: V字モデル＋段階ゲート（採用）

- 長所: 各成果物に検証が対応し、検証漏れが構造的に防げる。IPA の標準プロセスと整合。テーラリングで軽い変更にも適用可
- 短所: 段階の概念を全員（人・AI）が理解する必要がある（→ docs/process と skills で導線を用意）

### 案2: ライフサイクルを定義しない（従来どおりラウンドのみ）

- 長所: 軽量
- 短所: 要件・設計の検証対応が曖昧なまま。超上流軽視によるトラブル（IPA が指摘）を防げない

## Consequences（結果）

- 要件定義が実装前ゲートになる（ADR-0006 のトレーサビリティと連動）
- V字の右辺が段階ゲートの合格条件になり、`scripts/check.sh` の品質ゲートと接続する
- **再検討のトリガー**: 段階ゲートが軽い変更の律速になるなら、テーラリング基準を緩める
