# 0021: ソースリファレンスを shdoc で自動生成し、3層のドキュメントサイトとして公開する

- Status: Proposed
- Date: 2026-07-30
- Deciders: （PR レビュアー）

## Context（背景）

ADR-0020 で単一の `index.html` を GitHub Pages に置いたが、扱う内容が増えて1ページに収まらなくなった
（ADR-0020 の再検討トリガー「ページ数が増える」に該当）。加えて、**シェル関数 118 個・モジュール 26 本**
という規模のソースに対して API 相当のリファレンスが無く、実装を読む以外に全体像を把握する手段が無い。

制約:

- ADR-0003（土台はスタック非依存）— 外部依存を土台に持ち込むことに抵抗がある
- ADR-0004（品質ゲートの単一入口・ゲートを弱めない）
- 気づきカード #40（Round 9）— **任意ツールの有無で検査の判定が変わる状態を作らない**。判定不能は
  安全側に倒す
- Pages は `main` / `root` のブランチ配信（ADR-0020）。生成物を配信するには**リポジトリに置く**必要がある

## Decision（決定）

**ドキュメントサイトを3層に分割し、ソースリファレンスを shdoc で自動生成して、生成物をコミットしたうえで
品質ゲートで乖離を検査する。**

### 1. サイトを3層に分ける

| ファイル | 役割 |
|---|---|
| `index.html` | 優しい解説（初見向けの入口。比喩と具体例中心） |
| `guide.html` | 詳細解説（実務者向けの深堀り） |
| `reference.html` | **自動生成**のソースリファレンス |

Pages の配信方式は **`main` / `root` のまま変更しない**（ADR-0020 を維持。設定操作を不要にする）。

### 2. リファレンスは shdoc で生成する

- **shdoc**（MIT・reconquest/shdoc）を `tools/shdoc/` に **vendoring**（無改変・LICENSE 全文と出所を同梱）。
  ネットワーク非依存で再現でき、上流の変更に不意に追随しない。
- 注釈は **shdoc の標準タグ**（`@file` / `@brief` / `@description` / `@arg` / `@exitcode` / `@stdout` 等）を
  ソースのコメントとして書く。deb 独自記法を作らない。
- 生成器 `scripts/build-docs.sh` が `scripts/*.sh` ・ `mape/*.sh` ・ `.claude/hooks/*.sh` を shdoc に通し、
  Markdown を **依存ゼロの自前レンダラ**で単一の `reference.html` に変換する（shdoc は Markdown までしか出さない）。

### 3. gawk 依存を「ドキュメント生成に限定して」受け入れる

shdoc は `#!/usr/bin/gawk -E` を要求する。この依存を次の条件付きで受け入れる:

- **依存はドキュメント生成のみ**。品質ゲートの他の検査・hooks・MAPE-K は gawk 無しで動く
  （＝ gawk が無くても土台の本体機能は壊れない）
- **CI には gawk を導入する**（`checks.yml`）。ゲートが常に実効であることを保証する
- **gawk 不在時は「検査不能」として非ゼロで落ちる**。黙って合格にしない（気づきカード #40 の適用）

### 4. 生成物はコミットし、乖離を機械検査する

`scripts/build-docs.sh --check` を `scripts/check.sh` に配線する（`build-plugin.sh --check` と同じパターン）。
ソースの注釈を変えて再生成し忘れると CI が落ちる。生成器自体のテスト `scripts/test-build-docs.sh` も配線する。

生成は**決定論的**であること（生成日時・ホスト名・絶対パスを出力に混ぜない、`LC_ALL=C` で列挙順を固定）。

## Options Considered（検討した選択肢）

### 案1: shdoc を vendoring し、生成物をコミット＋乖離検査（採用）

- 長所: 注釈が**業界標準の記法**になり、他プロジェクトの知識が流用できる／将来 shdoc 本体に乗り換えても
  互換／生成物がリポジトリにあるので Pages 設定を変えずに配信できる／乖離が機械検査で落ちる／
  vendoring によりネットワーク非依存で再現可能。
- 短所: **gawk という外部依存が土台に入る**（ADR-0003 と緊張する）／生成物がリポジトリに入り差分が増える／
  再生成を忘れると CI が落ちる（ただしこれは意図した安全側の挙動）。

### 案2: 依存ゼロの自前ジェネレータ（不採用）

- 長所: 外部依存が一切増えず ADR-0003 に完全整合。既存の `# $1=...` 記法をそのまま読めるので
  ソースの書き換えが不要。
- 短所: 注釈記法が **deb 独自**になり、書き方を毎回説明する必要がある。パーサを自前で保守し続ける負債。
  「標準ツールを使う」という利用者の期待に反する。

### 案3: GitHub Actions でビルドして Pages へデプロイ（生成物を追跡しない）（不採用）

- 長所: リポジトリに生成物が入らず差分が綺麗。
- 短所: Pages のソースを「GitHub Actions」に切り替える**設定操作**が必要（ADR-0020 を supersede）。
  ローカルで生成結果を確認しづらく、乖離検査の位置づけも曖昧になる。今回の規模では過剰。

### 案4: 何もしない（README と guide だけ）（不採用）

- 長所: 追加ゼロ。
- 短所: 118 関数の全体像を掴む手段が実装を読むこと以外に無い状態が続く。

## Consequences（結果）

- 得るもの: ソースと乖離しない API リファレンス／標準記法による注釈／3層に分かれた読みやすい導線／
  注釈という形でソース自体の可読性も上がる。
- 失うもの: gawk 依存（ドキュメント生成に限定）／生成物のコミットによる差分増／再生成忘れで CI が赤になる手間。
- **再検討のトリガー**:
  - gawk 依存が運用の障害になった（利用者の環境で入らない等）→ 案2（依存ゼロの自前ジェネレータ）へ移行を検討
  - 生成物の差分が PR レビューを圧迫する → 案3（Actions ビルド配信）へ移行し ADR-0020 を supersede
  - ページ数がさらに増える／多言語化する → SSG の導入を新 ADR で検討
  - shdoc の上流が停止・ライセンス変更 → vendoring したまま fork 保守するか案2へ移行するかを再判断
