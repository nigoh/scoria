# トレーサビリティ管理（ID 体系と追跡規約）

ADR-0006 の詳細かつ **ID 体系の正本**。IPA の QFD に基づくトレーサビリティ管理（要件→設計→実装→
テストの一貫追跡）を翻訳。`scripts/check-traceability.sh` はこの規約に基づいて機械検証する。

## ID 体系

| 種別 | 形式 | 例 | 置き場所 |
|---|---|---|---|
| 機能要件 | `REQ-<領域>-<3桁>` | `REQ-AUTH-001` | `docs/requirements/` |
| 非機能要件 | `NFR-<分類>-<3桁>` | `NFR-SEC-001` | `docs/requirements/` |
| 設計判断 | `DES-<3桁>` | `DES-004` | 設計ドキュメント / ADR |
| テスト | `TEST-<レベル>-<3桁>` | `TEST-unit-012` | テストコード／テスト設計 |

- 領域・分類は英大文字の短縮語（AUTH, SEC, PERF …）。
- 連番はゼロ埋め3桁。採番は `/spec`・`/test-design` が自動化する。
- 一度発行した ID は再利用しない（削除された要件の ID は欠番のまま）。

## 追跡関係（トレーサビリティ・リンク）

各成果物は上流の ID を参照して繋がりを明示する:

```
REQ-AUTH-001 ──▶ DES-004 ──▶ (code) ──▶ TEST-unit-012
     │                                    TEST-acceptance-003
     └──────────────────────────────────▶（受入基準を検証）
NFR-SEC-001 ─────────────────────────────▶ TEST-system-005
```

- 設計ドキュメントは「実現する REQ/NFR」を明記する。
- テストは冒頭コメント／説明に「検証する REQ/NFR/DES」を `Verifies: REQ-AUTH-001` の形で記す。
- トレーサビリティ表（`templates/traceability-matrix.md`）で全体を俯瞰できる。

## 完全性の規約（機械検証される）

`scripts/check-traceability.sh` が以下を検査し、`scripts/check.sh` から呼ばれる:

1. **要件→テストの被覆**: `docs/requirements/` に現れる全 `REQ-*`/`NFR-*` が、リポジトリ内のどこかで
   `Verifies: <ID>` として少なくとも1回参照されている（＝対応テストがある）
2. **受入基準の存在**: 各要件ドキュメントに受入基準セクションがある
3. **ID 形式**: 発行された ID が上表の形式に沿う

要件ドキュメント（`docs/requirements/`）が空、または宣言された要件 ID が無い場合、このゲートは
「対象なし＝合格」を返す（スタック導入前でも壊れない。要件が宣言されると自然に有効化される。
現状は `docs/requirements/mape-k.md` の REQ/NFR が対象）。

## 参照キーワード（`Verifies:`）

テストと要件を結ぶキーワードは `Verifies:` に統一する。言語のコメント記法に依存せず、
行内に `Verifies: REQ-AUTH-001` という文字列が含まれればよい（複数 ID はカンマ区切り）。
これによりスタック非依存で追跡できる。
