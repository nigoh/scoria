# 超上流：要件定義（機能・非機能・受入基準・変更管理）

ADR-0006 の詳細。IPA の「超上流重視」「非機能要件の重視」「要件の合意及び変更ルールの事前確立」を翻訳。
要件定義成果物は `docs/requirements/` に置き、`/spec` スキルで作成する。

## なぜ超上流か

IPA/SEC はトラブルの主要因が上流（企画・要件定義）の欠陥にあると指摘する。要件の曖昧さ・非機能の
軽視・変更ルールの不在は、下流で増幅して大きな手戻りになる。**要件定義を実装前の段階ゲートに置く**
ことで、これを予防する（予防活動、ADR-0007）。

## 機能要件（REQ）

- `REQ-<領域>-<連番>` で採番する（例: `REQ-AUTH-001`）
- 各 REQ は「ユーザーストーリー（〜として、〜したい、なぜなら〜）」＋「受入基準」を持つ
- 受入基準は検証可能な形で書く（Given/When/Then など）。これが受入テスト（TEST-acceptance）の根拠になる

## 非機能要件（NFR）— 必ず一巡する

`NFR-<分類>-<連番>` で採番。以下のカテゴリを**必ず一巡して検討**し、対象外なら「対象外」と明記する
（検討漏れと「対象外の明示」を区別する）。分類は IPA/情報処理の非機能要求グレードを基にした既定セット:

| 分類 | 例 |
|---|---|
| 性能・効率性 | 応答時間、スループット、リソース使用量 |
| 信頼性 | 可用性、障害許容性、回復性、データ整合性 |
| 使用性 | 学習容易性、アクセシビリティ、多言語 |
| セキュリティ | 認証・認可、機密性、監査ログ、脆弱性対策 |
| 保守性 | 変更容易性、テスト容易性、モジュール性 |
| 移植性 | 環境依存、インストール性 |
| 運用性 | 監視、バックアップ、デプロイ、SLA/SLO |

各 NFR も受入基準（測定可能な閾値）を持つ。閾値の根拠を書く。

## 役割と責任（利害関係者）

IPA の「利害関係者の役割と責任分担の明確化」を翻訳。要件ごとに責任者（合意する人）を記録する。
Claude Code 環境では最小構成として次を区別する:

- **要求元**（何が欲しいか合意する人。多くはユーザー）
- **実装責任**（実装エージェント／人間）
- **検証責任**（テスト・レビュー）

## 変更管理（事前にルールを確立する）

要件の追加・変更・削除は次に従う（合意を後から覆さないため）:

1. 変更は要件 ID を明示して行う（どの REQ/NFR を変えるか）
2. 変更理由と影響（対応 DES/TEST、他要件との整合）を記録する
3. 受入基準も併せて更新する（基準なき要件を残さない）
4. 破壊的な変更・3成果物以上に跨る変更は先に ADR で合意する（ADR-0002）

## 段階ゲート（要件定義 → 設計）

次を満たしたら設計段階へ進める:

- [ ] 全 REQ に受入基準がある
- [ ] NFR カテゴリを一巡した（対象外は明示した）
- [ ] 各要件に責任者を記録した
- [ ] 要件の合意を記録した（イシュー／PR／トラッキング）

機械検証可能な項目（受入基準の存在・トレーサビリティ）は `scripts/check-traceability.sh` が担う。
