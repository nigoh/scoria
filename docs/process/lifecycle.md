# ライフサイクルと V字モデル・段階ゲート

ADR-0005 の詳細。開発の各段階と、それを通過するための段階ゲートを定義する。

## V字モデル

左辺で作り込み、右辺で検証する。各行の左右は対応し、右辺の検証が左辺の成果物を担保する。

```
 企画・要件定義 ─────────────────────────▶ 受入テスト / 妥当性確認
   （REQ / NFR / 受入基準）                    （TEST-acceptance）
      │                                            ▲
      ▼                                            │
   基本設計 ─────────────────────────────▶ システムテスト
   （DES: 外部仕様・アーキテクチャ）            （TEST-system）
      │                                            ▲
      ▼                                            │
   詳細設計 ─────────────────────────────▶ 結合テスト
   （DES: 内部仕様・IF）                        （TEST-integration）
      │                                            ▲
      ▼                                            │
   実装 ───────────────────────────────▶ 単体テスト
   （code）                                     （TEST-unit）
```

- 左辺の成果物には対応する右辺の検証が必ず存在する（トレーサビリティ、`traceability.md`）。
- 右辺の各テストレベルは、対応する左辺の成果物を根拠に設計する（`/test-design`）。

## 段階と成果物・ゲート

| 段階 | 主な成果物 | 段階ゲート（次段へ進む条件） |
|---|---|---|
| 企画 | 目的・スコープ・非機能の方向性 | `/round` でスコープと non-goals を合意した |
| 要件定義 | `docs/requirements/`（REQ/NFR/受入基準） | 全要件に受入基準がある。NFR カテゴリを一巡した。合意を記録した |
| 基本設計 | 設計ドキュメント / ADR（DES） | 要件との対応が取れている。重要判断は ADR 化した |
| 詳細設計 | 内部仕様・IF 定義 | 基本設計との対応が取れている |
| 実装 | コード | 詳細設計に沿う。保護ファイルを侵さない |
| テスト | TEST-unit/integration/system/acceptance | 各レベルが緑。全要件に対応 TEST がある（`check-traceability.sh`） |
| 運用・保守 | 障害対応・再発防止 | `/postmortem` で予防活動に接続（ADR-0007） |

段階ゲートは**人間または監査エージェント（process-auditor）が確認**する。機械的に検証できる部分
（トレーサビリティ完全性・受入基準の存在・テストの緑）は `scripts/check.sh` に組み込む（ADR-0004）。

## 見積り・スコープは段階的に確定する（多段階見積り）

IPA/SEC の「多段階の見積り方式」を翻訳。**初期の見積り・スコープは暫定**とし、目標値として固定しない。
不確実性が高いうちに下流の約束をせず、各段階ゲートで具体化に応じて見直す:

| 段階 | 見積り・スコープの粒度 |
|---|---|
| 企画 | 方向性・おおまかな規模感（幅を持たせる） |
| 要件定義 | 要件（REQ/NFR）が確定し規模が見える。スコープと non-goals を確定 |
| 設計 | 詳細見積り。実装工数・リスクが具体化 |

前段の暫定値を後段で無批判に確定値として扱わない。各ゲートで「見積りを見直したか」を確認する。

## テーラリングは2軸で決める（変更規模 × 対象の重要度）

IPA/SEC の「システムプロファイル」（人命・経済・公共・情報資産への影響で重要度を判定し、厳格さを
校正する考え方）を翻訳。**テーラリングは「変更規模」だけでなく「対象コンポーネントの重要度」の
2軸で決める。** 重要度が高い領域は、変更規模が小さくてもゲートを引き上げる。

### 軸1: 対象コンポーネントの重要度（システムプロファイル）

| 重要度 | 目安（影響） | 例 |
|---|---|---|
| 高 | 障害が人命・重大な経済損失・不可逆なデータ喪失・重大なセキュリティ侵害に直結 | 認証・認可、決済・課金、個人情報、マイグレーション、公開 API |
| 中 | 障害が機能停止・限定的な損失を招くが回復可能 | 主要業務ロジック、外部連携 |
| 低 | 障害の影響が軽微・局所的 | 表示調整、内部ツール、ドキュメント |

重要度は各アプリで `docs/requirements/` や設計時に識別する（対象領域に印を付ける）。

### 軸2: 変更規模 → 段階の省略目安

| 変更の規模 | 要件定義 | 設計 | テスト | テスト厳格度（ADR-0013） |
|---|---|---|---|---|
| 自明（typo・明白な1行バグ） | 省略 | 省略 | 再発防止テストのみ | test-first 省略可 |
| 小（局所的なバグ修正・小改修） | 軽（イシューに1〜2行） | 軽（必要なら ADR なしの判断） | 単体＋必要な結合 | 中核ロジックは test-first、瑣末は test-after 可 |
| 中（機能追加） | `/spec` で REQ/NFR/受入基準 | 基本＋詳細設計 | 全レベル | 純粋ロジックは test-first（赤を観測）標準 |
| 大（3成果物以上に跨る・破壊的） | 必須。先に ADR | 必須。ADR で記録 | 全レベル＋定量品質確認 | test-first＋エッジ多発コードは敵対的/property 必須 |

テスト戦術の選び分け（test-first／契約テスト先行／敵対的・property）は ADR-0013 と `.claude/rules/tdd.md`。
順序（red-first）は文化的規律、結果（被覆・緑・網羅率）は `check.sh`／`check-traceability.sh` で機械強制。

### 2軸の合成（重要度が省略を上書きする）

- **重要度「高」の領域は、変更規模に関わらず1段以上ゲートを引き上げる。** 例: 認証まわりの
  「小」変更でも、要件/受入基準の明記・境界/異常系・セキュリティ観点のテストを省略しない。
  重要度「高」は規模が小でも **test-first（赤を観測してから実装）を省略しない**（ADR-0013）。
- 重要度「高」× 大の変更は、`/spec`（NFR セキュリティ・信頼性を必ず）＋ `/test-design`（異常系・
  組み合わせ）＋ 定量品質確認まで通す。
- 重要度「低」× 自明は最軽量でよい。

判断に迷う場合は一段重い側を選ぶ。省略した段階はイシュー／PR に「なぜ省略したか（規模・重要度）」を1行残す。
