# PERSPECTIVES — MAPE-K 品質観点カタログ

MAPE-K の **Analyze が毎周回この観点を一巡**して「症状」を探すための観点集（ADR-0010/0011）。
「ありとあらゆる観点で見る」を体系化するため、骨格に **ISO/IEC 25010:2023**（プロダクト品質**9特性**。
2011 版の8特性に **Safety（安全性）** が加わり、Scalability が Flexibility 配下に昇格）を採り、
さらに **利用時の品質（Quality in Use）モデル**（プロダクト品質とは別モデル・5特性）と、web/app 実務の
横断観点（アクセシビリティ・国際化・プライバシー・観測可能性・SEO・法務/ライセンス・サステナビリティ・
倫理設計・DX 等）を足す。本リポジトリの NFR カテゴリ（`docs/process/requirements.md`）は現状プロダクト
品質側のみを持つため、Safety・互換性・利用時品質は**未収録の穴**（BACKLOG で補う）。

各観点は次の3層で書く:
- **見るポイント**: その観点で何を確認するか。
- **Monitor シグナル**: MAPE の Monitor が集める測定値。
- **土台での準備**: その観点を回すために要る仕組み（`scripts/check.sh` のゲート／`.claude/rules` の規約／
  skill／agent／ADR／MAPE 提案）。「開発すれば自動でこの観点が回る」状態にする。

> このカタログは土台（deb）由来で、記述にはスタック非依存を前提とした箇所が残る。Scoria は
> Vite + React + TypeScript のアプリなので（ADR-0024）、「スタック導入後」とある準備は**すでに
> 着手可能**なものとして読む。観点ごとの具体化は周回のなかで BACKLOG へ落としていく。

> 使い方（Analyze）: 毎周回、`knowledge/POLICY.md`（重点テーマ・却下ログ）を読んだうえで、本カタログの
> 各観点を一巡し、`mape/state/monitor.env` のシグナルと突き合わせて提案を作る。まだ仕組みが無い観点は
> 「準備の穴」を提案対象にする（例: 「a11y ゲートが check.sh に無い → 配線する rule/skill を用意」）。
> 提案は POLICY のリスク3分類（auto/approve/consult）で分け、インパクト×労力でスコアする。

## A. ISO/IEC 25010 プロダクト品質（9特性）

### 1. 機能適合性（Functional Suitability）
- 見るポイント: 完全性・正確性・目的適合性。要件（REQ/NFR）に受入基準があり、`Verifies:` でテストに結ばれているか。
- Monitor シグナル: 受入基準の充足率、要件被覆率（トレーサビリティ検査）、既知不具合数。
- 土台での準備: `docs/process`＋`scripts/check-traceability.sh` で被覆を機械検証済み（**あり**）。仕様レビュー skill `/spec`。

### 2. 性能効率性（Performance Efficiency）
- 見るポイント: 時間効率（レイテンシ）・資源効率（CPU/メモリ）・容量。web はバンドルサイズ・Core Web Vitals（LCP/CLS/INP）・N+1・キャッシュ。
- Monitor シグナル: p50/p95 レイテンシ、バンドル/アセットサイズ、Lighthouse Performance、メモリ、DB クエリ数。
- 土台での準備: **穴**。stack-init 時に「性能予算（budget）」ゲート雛形と rule を配線できるようにする。

### 3. 互換性（Compatibility）
- 見るポイント: 共存・相互運用。対応ブラウザ/デバイス/OS マトリクス、API 後方互換、文字コード。
- Monitor シグナル: サポート対象マトリクスの網羅、破壊的 API 変更、polyfill 差分。
- 土台での準備: **穴**。互換マトリクスの doc テンプレと「破壊的変更は `!`＋ADR」の規約（Conventional Commits は既にあり）。

### 4. 使用性 / UI・UX（Usability）
- 見るポイント: 習得性・操作性・UI の美しさ・ユーザーエラー防止。IA、レスポンシブ、空/エラー/ローディング状態、一貫性。
- Monitor シグナル: Lighthouse Best Practices、主要フローのクリック数/離脱、フォームエラー率。
- 土台での準備: **穴**。UI レビュー観点 skill、デザイン原則 rule、状態網羅（空/エラー/読み込み）チェックリスト。

### 5. 信頼性（Reliability）
- 見るポイント: 成熟性・可用性・障害許容性・回復性。エラーハンドリング、リトライ/バックオフ、タイムアウト、グレースフルデグレード。
- Monitor シグナル: エラーレート、可用性(SLO)、MTTR、フレーキーテスト率、リトライ発生数。
- 土台での準備: MAPE の circuit-breaker は運用ループの信頼性を担保（**部分的**）。アプリ向けは stack-init 時に health/リトライ規約を配線。

### 6. セキュリティ（Security）
- 見るポイント: 機密性・完全性・否認防止・責任追跡性・真正性。authn/authz、入力検証、シークレット、依存 CVE、サプライチェーン、セキュリティヘッダ。
- Monitor シグナル: 既知 CVE 数、秘密検出、権限境界の変更、依存の鮮度、監査ログ有無。
- 土台での準備: main 保護・force push 禁止・`.env`/鍵の deny は**あり**（hooks/settings）。**穴**: 依存脆弱性スキャン・秘密スキャンのゲート雛形。

### 7. 保守性（Maintainability）
- 見るポイント: モジュール性・再利用性・解析性・変更性・試験性。複雑度、重複、結合度、循環依存。
- Monitor シグナル: 複雑度、重複率、変更集中(churn)、ファイルサイズ、循環依存数。
- 土台での準備: 自己検証（validate-foundation）・churn 監視・skill-sync・行数予算は**あり**。**穴**: 複雑度/重複ゲート雛形。

### 8. 移植性（Portability）
- 見るポイント: 適応性・設置性・置換性。環境差異、設定外出し、コンテナ、ロックファイル管理。
- Monitor シグナル: 環境変数の外出し率、`.env.example` 鮮度、コンテナ再現性、OS 依存。
- 土台での準備: `.env.example`・ロックファイル直編集禁止は**あり**。**穴**: 環境再現の doc/コンテナ雛形。

### 9. 安全性（Safety, 25010:2023 で追加）
- 見るポイント: 運用上の制約・フェイルセーフ・危険警告・安全状態への復帰・ハザードの回避。**無人自律ループを持つ deb に直結**。
- Monitor シグナル: 危険操作の自動遮断回数、安全状態への復帰成功率、可逆性の担保。
- 土台での準備: MAPE の **circuit-breaker（連鎖失敗で停止）・赤→破棄・1周1件・consult 除外**は fail-safe の断片（**部分的**）。**穴**: これらを「安全性」として体系化する ADR と、危険操作の safe-state 定義。

## B. 横断・実務観点（web/app）

### 10. アクセシビリティ（Accessibility, a11y）
- 見るポイント: WCAG 2.2 A/AA、セマンティック HTML/ARIA、キーボード操作、フォーカス管理、コントラスト比、スクリーンリーダー、`prefers-reduced-motion`、代替テキスト。
- Monitor シグナル: axe 違反数、コントラスト不足、Lighthouse a11y スコア、キーボード到達不能要素。
- 土台での準備: **穴**。a11y チェックリスト skill＋stack-init 時に axe ゲートを配線する雛形。

### 11. 国際化・地域化（i18n / l10n）
- 見るポイント: 文言外出し、複数形、日付/数値/通貨の locale、タイムゾーン、RTL、文字幅。
- Monitor シグナル: 未翻訳キー数、ハードコード文言、locale 別崩れ。
- 土台での準備: **穴**。i18n 規約 rule＋未翻訳キー検出ゲートの雛形。

### 12. プライバシー・コンプライアンス（Privacy & Compliance）
- 見るポイント: PII の取り扱い、同意、GDPR/APPI、データ保持・削除、ログの個人情報マスキング。
- Monitor シグナル: PII を含むログ、保持ポリシー逸脱、同意フローの有無。
- 土台での準備: **穴**（consult 分類は POLICY にあり）。データ取り扱い ADR テンプレ＋ログ PII マスキング規約。**触るなら consult**。

### 13. 観測可能性（Observability）
- 見るポイント: 構造化ログ、メトリクス、分散トレース、アラート、SLO/エラーバジェット、相関 ID。
- Monitor シグナル: ログ構造化率、メトリクス/トレース網羅、アラート定義数、SLO 達成率。
- 土台での準備: MAPE の HEALTH 推移＝土台自身の観測（**部分的**）。**穴**: アプリ向けログ/メトリクス規約と HEALTH 拡張雛形。

### 14. 運用性 / DevOps（Operability）
- 見るポイント: デプロイ、ロールバック、設定外出し、feature flag、IaC、ゼロダウンタイム、DORA 指標。
- Monitor シグナル: デプロイ頻度・変更失敗率・MTTR・リードタイム（DORA）、CI 実行時間。
- 土台での準備: CI（checks.yml）は**あり**。**穴**: リリース/ロールバック手順 skill、DORA を HEALTH に載せる雛形。

### 15. SEO・発見可能性（Discoverability）
- 見るポイント: メタ/OGP、構造化データ、sitemap/robots、正規 URL、パフォーマンス（Core Web Vitals は順位要因）。
- Monitor シグナル: Lighthouse SEO、メタ欠落、構造化データ検証、被クロール性。
- 土台での準備: **穴**（web スタック時のみ該当）。stack-init 時に SEO チェックを配線する雛形。

### 16. コスト効率（Cost Efficiency）
- 見るポイント: リソース使用、CI 時間・コスト、クラウド課金、無駄なビルド/テスト。
- Monitor シグナル: CI 分数、ビルド時間、依存の重量、クラウドコスト。
- 土台での準備: **穴**。CI 時間を HEALTH に記録（gate_s は既にあり）→ アプリ CI 時間へ拡張。**課金に触るなら consult**。

### 17. データ整合性（Data Integrity）
- 見るポイント: マイグレーション、バックアップ/リストア、トランザクション、冪等性、スキーマ進化。
- Monitor シグナル: マイグレーション未適用、バックアップ鮮度、整合性違反。
- 土台での準備: **穴**（データに触るため慎重）。マイグレーション運用 ADR テンプレ。**触るなら consult**。

### 18. テスト網羅性（Test Coverage）
- 見るポイント: テストピラミッド（単体/結合/E2E/契約/プロパティ）、カバレッジ、フレーキー、回帰。
- Monitor シグナル: カバレッジ%、テスト種別の比率、フレーキー率、未テスト churn。
- 土台での準備: MAPE テスト・トレーサビリティ・`/test-design`・test-engineer は**あり**。**穴**: カバレッジ穴を MAPE 提案対象にする強化。

### 19. ドキュメント（Documentation）
- 見るポイント: 完全性・鮮度、CLAUDE.md/README/ADR の同期、オンボーディング、API ドキュメント。
- Monitor シグナル: ドキュメント鮮度（最終更新差）、リンク切れ、一覧と実体の乖離。
- 土台での準備: doc-auditor・skill-sync・ADR index 検査は**あり**。**穴**: リンク切れ/鮮度チェック。

### 20. 開発者体験 / DX（Developer Experience）
- 見るポイント: セットアップ容易性、CI 速度、エラーメッセージ、ローカル再現、lint/format 自動化、フィードバックループ。
- Monitor シグナル: セットアップ手順数、CI 時間、失敗時メッセージの分かりやすさ、初回ビルド時間。
- 土台での準備: session-start hook・単一ゲートは**あり**。**穴**: lint/format 自動化雛形、DX 計測。

### 21. AI 機能の安全性・公平性（該当時）
- 見るポイント: プロンプトインジェクション耐性、出力の安全性、秘密漏洩、バイアス/公平性、ハルシネーション対策。
- Monitor シグナル: 危険出力率、インジェクション試験の通過、機微情報の混入。
- 土台での準備: **穴**（AI 機能を作る場合のみ）。AI 安全レビュー観点 doc。**認証/データに触るなら consult**。

### 22. 法務・ライセンス・SBOM（Legal / Licensing）
- 見るポイント: リポジトリの `LICENSE`、依存の OSS ライセンス整合（コピーレフト混入）、サードパーティ表記、SBOM（CycloneDX/SPDX）、来歴（SLSA）。
- Monitor シグナル: ライセンス違反数、LICENSE 有無、SBOM 鮮度、非許可ライセンスの依存。
- 土台での準備: **穴**。`LICENSE` が**不在**（「コピーして使う土台」なのに再利用が法的に成立しない＝実欠陥）。license-scan ゲート雛形・SBOM 生成雛形も無い。**選定は人間＝consult**。

### 23. サステナビリティ / グリーン（Sustainability）
- 見るポイント: 計算資源・エネルギー効率、無駄な CI/ビルド、依存肥大、キャッシュ活用。
- Monitor シグナル: 依存重量、インストール秒、CI 分、再ビルド率（SCI 的指標）。
- 土台での準備: **穴**。CI ハング課金対策（timeout）は BACKLOG 済。`rules/sustainability.md` 雛形と依存重量シグナルが未整備。

### 24. テレメトリ・計測プライバシー（Telemetry Privacy）
- 見るポイント: 計測の**同意（opt-in）・最小化・DNT**、PII 非送出、保持/削除。プロダクト品質の機密性とは別軸の「計測設計」。
- Monitor シグナル: 既定 off か、同意フロー有無、送出データの PII 含有。
- 土台での準備: **穴**。deb 自身の `mape/state`（ledger/HEALTH）も自己テレメトリだが保持方針が未定義。**触るなら consult**。

### 25. インクルーシブ・倫理設計（Inclusive & Ethical Design）
- 見るポイント: ダークパターン回避、解約導線の対称性、強制/罠 UI 禁止、公平性、年齢・脆弱状況への配慮。a11y とは別軸。
- Monitor シグナル: ダークパターン検査、同意の誠実さ、公平性テスト。
- 土台での準備: **穴**。`/ethics-review` skill か `rules/inclusive-design.md` 雛形が無い。利用時品質（下記C）と接続。

## C. 利用時の品質（Quality in Use, 25010 別モデル）

プロダクト品質（A）とは**別モデル**。実利用者が目的を達成できるかを見る。deb の NFR は現状 A のみで、この5特性が要件・`/spec`・process-auditor に一度も現れない（**次元まるごとの穴**）。

| # | 特性 | 見るポイント | 土台での準備 |
|---|---|---|---|
| 26 | 有効性（Effectiveness） | 主要タスクを正確・完全に達成できるか（完了率） | 穴。受入基準を「タスク完了」で書く指針 |
| 27 | 効率性（Efficiency） | 目的達成に要する資源（時間・手順数） | 穴。主要フローの手順数バジェット |
| 28 | 満足性（Satisfaction） | 有用性・信頼・快適・満足（NPS/SUS 等） | 穴。満足度 SLI テンプレ |
| 29 | リスク回避性（Freedom from Risk） | 経済/健康/環境リスクの回避。**誤操作からの回復導線・エラーメッセージ品質** | 穴。error-message 規約（原因＋次の一手＋回復） |
| 30 | 利用状況網羅性（Context Coverage） | 想定内/想定外の利用状況を網羅（環境・言語・接続性） | 穴。対象利用状況を宣言する指針 |

## 準備状況サマリ（土台が今カバーしている／穴）

- **あり（体系化済み）**: 機能適合性・保守性(自己検証)・テスト網羅性(部分)・ドキュメント(部分)・セキュリティ(main保護/秘密deny)・信頼性(MAPEループ)・安全性(circuit-breaker=部分)。
- **穴（stack-init 時に配線する雛形・rule・skill を用意したい）**: 性能効率性・互換性・使用性/UI/UX・アクセシビリティ・国際化・プライバシー・観測可能性・運用性(DORA)・SEO・コスト・データ整合性・DX・AI 安全・サステナビリティ・テレメトリ設計・倫理設計。
- **次元まるごとの穴（要件体系に無い）**: **安全性(Safety, 25010:2023)**・**互換性(NFR7分類に欠落)**・**利用時の品質(QoU 5特性)**・**法務/ライセンス(LICENSE 不在)**。ここは ADR で要件体系側を拡張する必要がある。

> この「穴」の一覧が Analyze の継続的な提案源になる（周回ごとに1つずつ土台の準備を厚くしていく）。
> 具体の提案は `knowledge/BACKLOG.md` に、周回の考察は `knowledge/PROGRESS.md` に蓄積する。
